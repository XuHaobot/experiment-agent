# ResearchOS V2.5 — 架构探索、产品设计与可行性分析报告

> **文档定位**：ResearchOS V2.5 核心架构设计与战略演进蓝图 (SSOT Architecture Discovery)  
> **演进主题**：**Personal Research Space × Local AI × Obsidian Knowledge Layer**  
> **基准版本**：ResearchOS V2.4.0 (闭环功能全部就绪，9/9 测试通过)  
> **设计原则**：
> * **User owns the data.** (科研数据属于科研人员自己，严禁无感知云端泄露)
> * **User owns the knowledge.** (科研知识沉淀在开放通用的 Markdown 笔记库中，拒绝专有格式锁定)
> * **User owns the research history.** (因果血缘与运行遥测完整归档，历史可追溯、可复现)
> * **AI assists exploration.** (AI 专注于消除认知不确定性与提供反向思考，严防自我强化固化)
> * **AI does not own the truth.** (事实由真实物理沙箱执行与可溯源证据切片决定，AI 解释不可直接升级为科学真理)

## 1. V2.4 → V2.5 为什么升级

在 **ResearchOS V2.4.0** 中，我们完成了科研闭环的“功能型落地”：
* 文献检索、本地 PDF 解析与 `Page X · Section Y · Para #Z` 证据切片；
* 多表 Schema 关联探测与 DuckDB 交互式统计分析向导；
* 基于科研上下文的 Python 代码生成、受控沙箱运行与智能 Debugger；
* 零幻觉科研记忆分级 (`SUPPORTED` / `UNSUPPORTED`) 与反向多跳因果溯源。

**但是，通过真实科研可用性验证 (V2.4 Validation)，我们发现了深层次的产品断层：**

```text
       ┌─────────────────────────────────────────────────────────────┐
       │                 科研人员日常的核心生产力习惯                 │
       │  (习惯在 Obsidian / 本地 Markdown 中写思考，有强烈的隐私要求)  │
       └──────────────────────────────┬──────────────────────────────┘
                                      │ 割裂断层
                                      ▼
       ┌─────────────────────────────────────────────────────────────┐
       │                   ResearchOS V2.4 现状                      │
       │  (数据封闭在自身的 JSON/SQLite 中，依赖外部云端 LLM，缺乏对抗思考) │
       └─────────────────────────────────────────────────────────────┘
```

1. **知识割裂（孤岛效应）**：科研人员已经拥有建立多年的个人知识库（如 Obsidian、Logseq、本地 Markdown），他们不想把思考迁移到另一个封闭的 Web 数据库里。
2. **隐私与合规风险**：未发表的实验测量数据、临床患者样本、专利前实验代码绝对不能直接作为 Prompt 发往云端大模型，急需**纯离线 Local AI** 与**严格的隐私边界闸门**。
3. **AI 认知固化风险 (Epistemic Lock-in)**：AI 如果只根据历史结论推荐“更有可能提升指标”的实验，会导致研究视野迅速收窄，忽视潜在的反例与替代假说。

**因此，V2.5 不是简单的“加两个插件”，而是将 ResearchOS 从“独立的实验辅助 Web 应用”升维为“以科研人员为中心的个人研究空间 (Personal Research Space)”。**

## 2. V2.5 核心产品定位：Personal Research Space

**ResearchOS V2.5 绝不做 SaaS 化云端平台，坚守 Local-First 桌面级科研操作系统。**

```text
                      Personal Research Space (V2.5)
┌──────────────────────────────────────────────────────────────────────────┐
│                                                                          │
│   [Personal Knowledge Layer]             [Structured Execution Layer]    │
│         (Obsidian Vault)                        (ResearchOS Core)        │
│   • 自由思考与文献笔记                     • 真实受控沙箱 (RestrictedPython)  │
│   • 双向链接网与 Canvas 白板                • 本地极速分析 (DuckDB/SQLite)     │
│   • 开放通用 Markdown 存储                 • 拓扑血缘与因果图谱 (Lineage Graph)│
│                                                                          │
│               │                                   │                      │
│               └─────────────┬─────────────────────┘                      │
│                             ▼                                            │
│                 [Local Privacy & AI Gateway]                             │
│         • 敏感数据拦截 (ALLOW / ASK / DENY)                               │
│         • 本地大模型优先 (Ollama / llama.cpp / LM Studio)                 │
│         • 对抗式假说推演 (Anti-Lock-in & Exploration)                    │
│                                                                          │
└──────────────────────────────────────────────────────────────────────────┘
```

### 核心定位三要素
1. **数据与知识主权**：所有资产以标准文件（Markdown / JSON / CSV / PNG）保存在用户指定的本地磁盘路径，用户随时可以用任何外部编辑器打开，绝不绑定专有格式。
2. **双层互补协同**：非结构化的个人知识与自由笔记归 Obsidian；结构化的实验设计、物理运行、代码执行与数据血缘归 ResearchOS。
3. **安全受控智能**：本地模型处理敏感数据，云端模型仅在显式授权时处理脱敏公开信息。

## 3. Obsidian 的正确定位：四大方案深度比对与裁决

### 3.1 方案比对

| 方案 | 架构模式 | 优势 | 致命缺陷 | 裁决 |
| :--- | :--- | :--- | :--- | :--- |
| **方案 A** | ResearchOS → 单向导出 → Obsidian | 实现简单，完全解耦 | 导出即过时，在 Obsidian 里的修改无法反馈给 Agent，形成信息孤岛 | ❌ 否决 |
| **方案 B** | ResearchOS ↔ 双向硬同步 ↔ Obsidian Vault | 实时双向读写同一批文件 | 产生严重的双数据库并发冲突、Markdown 格式被破坏、元数据丢失 | ❌ 否决 |
| **方案 C** | **Obsidian = 个人知识与笔记层<br>ResearchOS = 结构化科研与执行层** | **职责清晰、互不污染；通过 Stable ID 与 URI 双向联动；无数据库冲突** | **需规范 Markdown YAML Frontmatter 协议** | 🟢 **强烈推荐** |
| **方案 D** | ResearchOS 直接重做成类似 Obsidian 的 Markdown 编辑器 | 体验完全一体化 | 重复造轮子，开发成本巨大，难以匹敌 Obsidian 庞大的插件生态 | ❌ 否决 |

### 3.2 方案 C 推荐架构细节 (The Unified Synergy Model)

```text
    Obsidian (Personal Knowledge Layer)          ResearchOS (Structured Execution Layer)
   ┌───────────────────────────────────┐        ┌───────────────────────────────────┐
   │ • 自由撰写的科研笔记与灵感           │        │ • Project / Hypothesis 状态机     │
   │ • 读书笔记与文献 Callout 引用      │        │ • Python / DuckDB 受控执行沙箱     │
   │ • Obsidian Graph View / Canvas    │        │ • 物理 Run 遥测与数据血缘 Lineage  │
   │ • Dataview 看板查询                │        │ • ToolRegistry & HITL 权限工单    │
   └─────────────────┬─────────────────┘        └─────────────────┬─────────────────┘
                     │                                            │
                     │                 [Vault Bridge]             │
                     │  (Stable YAML Frontmatter + [[Wikilinks]]) │
                     └───────────────────────┬────────────────────┘
                                             ▼
                             本地工作空间磁盘目录 (Local File System)
                             ├── 01_Projects/
                             ├── 02_Hypotheses/ (含 YAML + 双链)
                             ├── 03_Literature/ (PDF 切片笔记)
                             ├── 04_Experiments/ (实验方案与脚本)
                             ├── 05_Conclusions/ (原子结论笔记)
                             └── 06_Artifacts/ (生成的图表与分析表)
```

* **单一可信源原则 (Single Source of Truth)**：
  * 实验状态、Run 遥测、因果拓扑血缘的 SSOT 在 **ResearchOS**；
  * 科研人员的主观思考、文献阅读批注、假设推演灵感的 SSOT 在 **Obsidian 笔记**。
* **文件同步机制**：
  * ResearchOS 在执行实验或沉淀结论时，自动在用户 Vault 对应目录更新/创建对应的 `.md` 实体文件；
  * 每个 `.md` 文件顶部包含标准 YAML Frontmatter（包含稳定 `id`、`entity_type`、`status` 等），正文包含 `[[Wikilinks]]`；
  * 科研人员在 Obsidian 中可直接编辑正文内容；ResearchOS 仅通过只读解析提取带有标签的笔记作为 Agent 上下文，绝不破坏用户自行编写的笔记排版。

## 4. Local-First 架构与数据主权分级

科研数据的保密性要求极其严格。V2.5 建立明确的**四级数据分级矩阵**：

```text
[L0: 完全公开] ──> 开放学术检索 (OpenAlex/arXiv) ──> 可直接调用云端 API
[L1: 脱敏摘要] ──> 课题标题、假说陈述、统计指标 ──> 经用户授权可调用云端 LLM
[L2: 内部科研] ──> 实验代码、未发表 PDF、分析脚本 ──> 默认仅限本地 Local AI
[L3: 核心机密] ──> 原始 CSV/Parquet、患者/商业数据 ──> 严禁输入任何模型 (仅沙箱物理执行)
```

| 数据类型 | 级别 | 物理存储位置 | 是否允许发送给云端 LLM | 是否允许发送给 Local AI | 允许的处理动作 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **已发表论文元数据 / 标题** | L0 | `data/papers/` | ✅ 允许 (ALLOW) | ✅ 允许 | 语义检索、学术问答 |
| **脱敏统计指标 (p值/均值/方差)** | L1 | `data/artifacts/` | 🟡 需确认 (ASK) | ✅ 允许 | 报告生成、结论推演 |
| **课题假说与研究问题描述** | L1 | `data/hypotheses/` | 🟡 需确认 (ASK) | ✅ 允许 | 假说反思、实验建议 |
| **未发表论文 PDF 原文与切片** | L2 | `data/papers/{id}/` | ❌ 默认禁止 (DENY) | ✅ 允许 (Local) | 本地 RAG、段落切片提取 |
| **实验 Python 源代码与参数** | L2 | `data/experiments/` | ❌ 默认禁止 (DENY) | ✅ 允许 (Local) | 本地生成、沙箱 Debugger |
| **实验原始数据集 (CSV/Parquet)** | L3 | `data/datasets/` | 🚫 **绝对禁止 (DENY)** | 🚫 **绝对禁止 (DENY)** | **仅限 DuckDB 本地物理查询** |
| **系统敏感信息 (API Key/绝对路径)**| L3 | 本地内存 / `.env` | 🚫 **绝对禁止 (DENY)** | 🚫 **绝对禁止 (DENY)** | 本地权限校验 |

## 5. Local AI Gateway：本地与云端模型统一抽象层

### 5.1 统一接口设计 (`LLMProvider` 抽象)

```python
class LLMProvider(ABC):
    """大模型统一接入协议 (支持本地与云端零摩擦切换)"""
    name: str
    is_local: bool
    context_window: int

    @abstractmethod
    async def chat_complete(
        self,
        messages: list[dict[str, str]],
        temperature: float = 0.2,
        stop: list[str] | None = None,
    ) -> str:
        """标准文本生成"""
        pass

    @abstractmethod
    async def stream_chat(
        self,
        messages: list[dict[str, str]],
        temperature: float = 0.2,
    ) -> AsyncGenerator[str, None]:
        """SSE 流式输出"""
        pass
```

### 5.2 Provider 矩阵

```text
LLMProvider (统一抽象)
├── 🖥️ Local Providers (纯离线私有化)
│   ├── OllamaProvider (标准端点: http://localhost:11434/v1)
│   ├── LlamaCppProvider (轻量级嵌入式/本地服务器: http://localhost:8080/v1)
│   └── LMStudioProvider (桌面端本地推理服务: http://localhost:1234/v1)
│
└── ☁️ Cloud Providers (公网高性能大模型)
    ├── OpenAICompatibleProvider (DeepSeek / Qwen / 通义千问等兼容 API)
    ├── GeminiProvider (Google Gemini API)
    └── AnthropicProvider (Claude API)
```

### 5.3 本地硬件自适应与模型推荐规格
* **8GB 显存 / 16GB 内存**：推荐 `qwen2.5:7b-instruct-q4_K_M` 或 `llama3.1:8b-instruct-q4_K_M` (兼具代码生成与学术问答，显存占用约 5.2GB)。
* **16GB+ 显存 / 32GB 内存**：推荐 `qwen2.5:14b-instruct-q4_K_M` 或 `deepseek-coder-v2:16b` (高精确定理推导与复杂 SQL 编写)。
* **纯 CPU 运行环境**：通过 `llama.cpp` 提供轻量量化模型推理，自动降频运行，保障基础问答可用。

## 6. Privacy Boundary：三级隐私权限网关

在所有 Agent 调用模型前，必须经过 **Privacy Gateway** 的强制拦截与脱敏流水线：

```text
[待发送的 Prompt 上下文]
           │
           ▼
┌──────────────────────────────────────┐
│       Privacy Gateway 检查器         │
└──────────────────┬───────────────────┘
                   │
    ┌──────────────┼──────────────┐
    ▼              ▼              ▼
 [ALLOW]         [ASK]          [DENY]
 (直接放行)   (弹窗人工授权)  (硬性阻断并告警)
    │              │              │
    │        [用户点击批准]        └──> 抛出 PrivacyViolationError
    │              │                   (并记录本地审计日志)
    ▼              ▼
┌──────────────────────────────────────┐
│  安全脱敏流水线 (Data Sanitizer)     │
│  • 抹除本地机器绝对路径 (/Users/...)   │
│  • 抹除真实 API Key / 租户 ID        │
│  • 仅保留数据 Schema，剥离真实数据行    │
└──────────────────┬───────────────────┘
                   │
                   ▼
       发送至已选定的 LLMProvider
```

### 三级状态判定规则
1. **`ALLOW`**：仅包含公开学术文献标题、已知公开常识、用户手写通用科研问题。
2. **`ASK`**：包含当前课题未发表假说描述、实验超参数设计、由 DuckDB 计算得出的统计汇总指标；前端弹出确认模态框：“*正在向 [模型名称] 发送以下研究上下文，是否授权？*”。
3. **`DENY`**：包含 CSV/Parquet 表格真实行数据、包含绝对文件系统路径、包含 `.env` 凭证；系统静默拦截，提示 Agent 只能使用 Schema 抽象生成代码。

## 7. Research Memory 2.0：十级事实语义重构

为了彻底杜绝大模型在长期科研交互中将“猜测”误记为“真理”，Research Memory 2.0 确立**十级严格语义实体分类**：

```text
                              客观物理世界 (Physical Grounding)
                                              │
       ┌───────────────────┬──────────────────┴───────────────────┐
       ▼                   ▼                                      ▼
[OBSERVATION]           [EVIDENCE]                             [FACT]
 (原始日志/观测数据)   (锚定 PDF/Run 的精确证据切片)          (经多源证据强支撑的客观事实)
       │                   ▲                                      ▲
       │                   │ (实验验证 / 统计显著)                  │ (反向溯源确认)
       ▼                   │                                      │
[INTERPRETATION] ──> [HYPOTHESIS] ───(验证成功)───> [CONCLUSION] ─┘
 (对数据的理论解释)    (待检验科学假说)             (沉淀的原子科研结论)
                           ▲
                           │ (经人工/实验验证)
                     [AI_SUGGESTION]
                      (AI 提出的启发式建议，严禁自动升为 FACT)

─────────────────────────────────────────────────────────────────────────────
补充反思分类 (Negative & Human Knowledge):
• [FAILED_EXPERIMENT] : 明确失败的运行实例与参数崩溃区间 (极高探索价值)
• [ASSUMPTION]        : 实验设计的前提假设 (如假设噪声符合高斯分布)
• [USER_BELIEF]       : 科研人员个人的主观直觉与经验法则 (标记为 subjective)
```

### 严格状态机晋升规则
* **禁止跨级直升**：`AI_SUGGESTION` 绝不能直接写入 `FACT` 数据库。
* **晋升路径**：`AI_SUGGESTION` $\rightarrow$ 用户采纳创建 `HYPOTHESIS` $\rightarrow$ 执行沙箱 `RUN` $\rightarrow$ 提取 `EVIDENCE` $\rightarrow$ 沉淀 `CONCLUSION` $\rightarrow$ 记入 `FACT`。

## 8. AI Anti-Lock-in 机制：抗认知固化与假说对抗体系

### 8.1 认知固化 (Epistemic Lock-in) 的危害
在传统科研 Copilot 中，AI 会倾向于顺从用户的既有假说，并在后续分析中反复引用过去的结论，导致：
* 对反常数据（Outliers）视而不见；
* 不断在狭窄的局部最优参数区间内打转；
* 忽视根本性的替代解释（Alternative Hypotheses）。

### 8.2 假说对抗机制 (Adversarial Hypothesis Testing)
在 V2.5 中，每次评估假说或生成结论时，Agent 强制执行**对抗式双轨检索与论证**：

```text
                           评估目标假说 H1
                                 │
                 ┌───────────────┴───────────────┐
                 ▼                               ▼
       [正向论证轨道 (Support)]         [对抗反驳轨道 (Adversarial)]
       • 检索支撑 H1 的 Evidence         • 检索反驳 H1 的反例证据
       • 寻找符合预期的实验 Runs         • 寻找在相同参数下崩溃的 Runs
       • 提取文献中的同向结论           • 提出 1~2 个相互竞争的替代假说 (H_alt)
                 │                               │
                 └───────────────┬───────────────┘
                                 ▼
                    [综合置信度与盲区评估]
              • 若只有正向证据而无负向检验 ──> 标记为 "HIGH_UNCERTAINTY"
              • 强制输出: "可能推翻该假说的潜在风险点"
```

## 9. Research Exploration Engine：基于不确定性消除的实验探索

### 9.1 探索-利用平衡 (Exploration vs. Exploitation)
在推荐下一组实验方案时，引擎不仅计算“预期指标提升（Exploitation）”，更计算**“信息增益与不确定性消除量（Exploration）”**：

$$\text{Score}(Exp) = \alpha \cdot \text{InfoGain}(\Delta \text{Uncertainty}) + \beta \cdot \mathbb{E}[\text{MetricGain}] - \gamma \cdot \text{Cost} - \delta \cdot \text{Redundancy}$$

```text
已知区域 (Known Space)                  未知探索空间 (Unknown Space)
├── Supported (已有高信度实验支撑)        ├── Untested (参数空间从未采样的空白区)
├── Refuted (已证实无效/过平滑区域)       ├── Underexplored (样本稀疏或边界模糊区)
└── Conflicted (文献与实测相互矛盾)       ├── Competing (可区分 H1 与 H2 的决断实验)
                                        └── Blind Spot (长期被忽略的超参交互项)
```

### 9.2 推荐理由透明化 (Why this Experiment?)
Next Experiment 的推荐输出中，严禁只输出代码或参数，必须包含结构化的科学推演依据：
```json
{
  "title": "Ablation on Higher Graph Update Rate (k=24, rate=0.8)",
  "strategy": "BOUNDARY_EXPLORATION",
  "why_this_experiment": [
    "1. 历史 Run #02 (k=20) 达到当前最优，但 k ∈ [21, 25] 区间仍为未采样空白区；",
    "2. 假说 H1 认为更新率提高可抑制噪声，而文献 Paper #04 警告过高更新率会导致拓扑高频抖动；",
    "3. 本实验设计为决断实验 (Discriminative Run)，旨在明确区分两种理论预期的拐点位置。"
  ],
  "uncertainty_to_reduce": "明确动态图更新率在噪声环境下的理论稳定性上限。"
}
```
