# ResearchOS V2.5 — Phase 17 代码与认识论架构审计报告

> **审计对象**：ResearchOS 核心记忆系统、因果链条、Next Experiment 引擎与 Obsidian 知识桥接  
> **审计日期**：2026-08-31  
> **审计目标**：评估当前 Memory 机制存在的“AI 认知固化 (Epistemic Lock-in)”风险，明确 Phase 17 最小改造点。

---

## 一、九大核心问题审计结论

### 1. 当前 Research Memory 已经保存了什么？
* **存储聚合范围** (`backend/domain/memory.py`)：
  - 课题核心问题 (`core_questions`)
  - 假说状态划分 (`hypotheses_state: supported / testing / refuted`)
  - 历史实验物理运行指标 (`runs: metrics, parameters, status`)
  - 已沉淀的科研结论 (`established_facts: statement, confidence, evidence_sources`)
  - 文献列表 (`papers: title, year, doi`) 与数据集元数据 (`datasets`)
  - 粗粒度的五态科研状态 (`known`, `tried`, `failed_or_refuted`, `unknown_uncertainty`, `next_priorities`)。
* **现状缺陷**：所有信息混在一起被视作“事实”，缺乏严格的认识论状态标签（如无法区分真实的客观测量 vs AI 生成的推测性总结）。

---

### 2. 当前 Memory 是如何被 Agent 使用的？
* `query_research_memory(project_id, question)` 被前端问答及 Agent 决策调用。
* Agent 从 Memory 中提取“最佳运行 (`best_run`)”与“已知事实 (`established_facts`)”，拼接为静态上下文 Prompt，并直接向 LLM 或启发式逻辑提问。
* **认知固化隐患**：Agent 倾向于围绕已经取得高准确率的历史参数（如 `best_run`）继续在其邻域内给建议，而忽略了背后的反面证据或根本性竞争假设。

---

### 3. 当前 Conclusion / Evidence / Hypothesis 是什么关系？
* **领域实体关系**：
  - `Hypothesis` 包含 `evidence: [ev_1, ev_2, ...]` 与 `status: testing / supported / refuted`；
  - `Evidence` 来源于 `Paper` 切片 (`ev_pdf_...`) 或实验运行 (`run_...`)，携带 `snippet`、`supports` 极性与来源定位；
  - `Conclusion` 关联一个 `hypothesis_id`，并记录 `evidence_refs: [{"type": "...", "id": "...", "snippet": "..."}]`。
* **闭环断点**：结论通常只汇总了支持假说的正向证据，当存在相互矛盾或未解释的失败运行时，缺少专门的 **Evidence Balance (支持/反驳/未知)** 结构化平衡视图。

---

### 4. 当前哪些信息属于事实 (FACT)？
* **真正的科学事实与硬性观察 (FACT / OBSERVATION)**：
  - 实验执行遥测数据：`Run` 实际使用的超参数 `actual_parameters` 与程序输出的真实物理指标 `metrics`（如 `accuracy=0.91`, `loss=0.12`）；
  - 数据集模式与字段统计（由 DuckDB 执行返回的均值、分位数、缺失率）；
  - 文献原文精准切片（带有 `Page X · Sec Y · MD5` 的精确原句引用）；
  - 代码沙箱抛出的具体异常栈 (`Traceback`)。

---

### 5. 当前哪些信息可能只是 AI 推测 (AI_SUGGESTION / INTERPRETATION)？
* `Analysis Wizard` 生成的自然语言归因解释；
* `Debugger` 自动生成的错误诊断结论与补丁建议；
* `Next Experiment` 推荐理由 (`rationale`) 与预期效果 (`expected_outcome`)；
* 假说分析中的所谓“过平滑”或“分布偏移”等宏观机理解释。
* **当前风险**：这些未经验证的 AI 观点一旦被存入 `Conclusion` 或 `Memory`，后续会被系统当作既定事实再次引用，产生**自强化回音室**。

---

### 6. 当前 Next Experiment 是否可能重复过去的思路？
* **是，存在较高复读与局部收敛风险**：
  - `recommend_next_experiments` 主要依赖 prompt 提取历史实验趋势；
  - 启发式规则也是在 `best_run` 邻域做微调；
  - 没有显式计算 **Unexplored Space（未探索参数空间）**，容易漏掉未测试的参数区间；
  - 没有引入 **Alternative Hypotheses（竞争性假说）**，导致实验设计单一化。

---

### 7. 当前 Obsidian 用户笔记是否已经进入 Research Memory？
* **未自动进入，保持了解耦**：
  - Phase 16 的 Vault Bridge 仅将 ResearchOS 实体单向导出到 Markdown；
  - 用户在 `## My Notes` 中写的个人观点保留在本地 Markdown 中；
  - Frontmatter 预留了 `epistemic_status`，但尚未在 Memory 查询引擎中实现分级加载与 `USER_BELIEF` 语义识别。

---

### 8. 当前本地 AI / Cloud AI 是否都经过 Privacy Gateway？
* **是，已由 Phase 15 严格把守**：
  - 所有 LLM 调用统一经过 `src/llm_client.py` -> `LLMGateway` -> `PrivacyGateway`；
  - 四级分类 (`PUBLIC`, `INTERNAL`, `SENSITIVE`, `RESTRICTED`) 与三级门禁 (`ALLOW`, `ASK`, `DENY`) 保证了未授权敏感数据不会离机；
  - Phase 17 的 Memory 改造完全在 Domain 层运行，天然受 Privacy Gateway 保护。

---

### 9. Phase 17 最小改造点是什么？
1. **定义 10 级 Epistemic Status 枚举** (`OBSERVATION`, `FACT`, `EVIDENCE`, `INTERPRETATION`, `HYPOTHESIS`, `CONCLUSION`, `FAILED_EXPERIMENT`, `ASSUMPTION`, `USER_BELIEF`, `AI_SUGGESTION`)；
2. **升级 `backend/domain/memory.py`**：
   - 区分 Evidence 的正反极性，构建 `EvidenceBalance`；
   - 提取并维护 `unexplored_space`（参数网格盲区探测）；
   - 启发式/结构化生成 `alternative_hypotheses`（竞争性假说，标记为 `AI_SUGGESTION`，附带 `reasoning_basis`）；
   - 保持 `query_research_memory` 向下兼容，输出包含 `epistemic_status`, `supporting_evidence`, `contradicting_evidence`, `failed_experiments`, `alternative_hypotheses`, `unexplored_space`；
3. **改造 `backend/domain/next_experiment.py`**：
   - 推荐引擎增加 `information_gain` 与 `uncertainty_reduced` 计算，优先针对未探索空间与竞争性假说设计实验；
4. **前端面板适配** (`ConclusionPanel.vue` / `NextExperimentPanel.vue` / `ProjectDetailView.vue`)：
   - 显示 Evidence Balance（支持 vs 反驳 vs 未知）；
   - 显示 Alternative Hypotheses（带有 `AI Suggestion` 徽章）；
   - 显示 Unexplored Space；
5. **单元测试与回归套件** (`tests/test_v25_phase17_memory.py` + 全部旧用例 100% PASS)。
